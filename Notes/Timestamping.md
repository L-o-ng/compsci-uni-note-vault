A **timestamp** is a *unique* identifier $TS(T_{i})$ that indicates the *relative starting time* of a transaction $T_{i}$.
It is usually generated by the system clock or a logical counter.
## Methodology
Timestamps determine the *serialisability* **order**.
Two transactions $T_{1},T_{2}$ obtain timestamps $TS(T_{1})<TS(T_{2})$. This indicates that in the serialised schedule, $T_{1}$ is scheduled **before** $T_{2}$.

The protocol also maintains for each data item $x$ two values:
1. $WTS(x)$, or the **writing timestamp**: the *largest* timestamp of a transaction that executed `write(x)` successfully
2. $RTS(x)$, or the **reading timestamp**: the *largest* timestamp of a transaction that executed `read(x)` successfully.

This ensures that conflicting read and write operations are executed in timestamp order: suppose that transaction $T$ issues `read(x)`:
+ If $TS(T)<WTS(x)$:
	+ An earlier transaction $T$ is trying to read a value of an item that has been updated by a later transaction;
	+ Then, the operation rejects and $T$ is rolled back.
+ If $TS(T)\geq WTS(x)$:
	+ The `read(x)` operation is executed;
	+ $RTS(x)$ is set to the *maximum* of $TS(T)$ and the current value for $RTS(x)$.

And similarly, for a `write(x)`:
+ If $TS(T)<RTS(x)$:
	+ A later transaction than $T$ uses the current value of $x$, and it would be dangerous for $T$ to update it;
	+ Then, the operation rejects and $T$ is rolled back.
+ If $TS(T)<WTS(x)$:
	+ Transaction $T$ attempts to write an obsolete value of $x$;
	+ Then, the operation rejects and $T$ is rolled back.
+ Otherwise:
	+ The operation is executed;
	+ We set $WTS(x)=TS(x)$.

## Recoverability
See first [[Recoverable Schedule]].

The timestamping protocol guarantees serialisability, since all the arcs in the precedence graph are from a transaction with a **smaller** timestamp to one with a larger timestamp. There **cannot** be cycles.
This ensures freedom from [[Deadlocks under DBMS Locking Systems|Deadlocks]], but the schedule may not be recoverable, and thus not [[Locking#Cascading Rollback|Cascadeless]].
### Cascade Freedom
Suppose $T_{i}$ aborts, but $T_{j}$ has read a data item written by $T_{j}$. Then, $T_{j}$ must abort: if $T_{j}$ has been allowed to commit earlier, then the schedule is **not** recoverable.
Any transaction that reads an item written by $T_{j}$ must reject - this leads to cascading rollback.

We therefore structure transactions such that **all** *writes* are performed at the **end** of processing.
All writes form an [[Transactions#Atomicity|Atomic]] action: no transaction may execute while a transaction is being written. A transaction that aborts is restarted with a **new** timestamp.
